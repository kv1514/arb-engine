### 1.4 Proposed provenance policy

Nothing is deleted or rewritten; the debt is made visible and prevented from growing.

1. **Provenance travels in the fixture, not in `out/`.** Because `out/` is git-ignored, an
   external record can never verify a checkout. Every published fixture carries a `_provenance`
   block: `script`, `argv`, `git_head` (full sha), `git_dirty`, `generated_utc`, `inputs`
   (fold/date range plus a fingerprint of each input database).
2. **Refuse to write an unprovenanced fixture.** `microstructure_eval.py` should decline to write
   into `tests/fixtures/` when `git_head` is null, the tree is dirty, or the results path is
   outside the repository — the three conditions that produced today's untraceable files.
3. **Record the input identity.** Every run reads another clone's live `history.db`. Log its path
   plus a cheap fingerprint (row counts per table and max `ts`) so a replay can be shown to have
   read the same data.
4. **A spec-hash change needs a reason.** When `spec_hash` differs from the previous run of the
   same fold, require `reopen_reason` or mark the run `exploratory: true` automatically.
5. **Keep the log append-only.** Corrections go in a sibling `annotations.jsonl`, never by editing
   history.
6. **Enforce it in the suite.** `tests/test_results_provenance.py` (added by this audit) requires a
   `_provenance` block on every fixture, with the 16 legacy files listed by name and reason in
   `UNVERIFIED_PROVENANCE`. Listing is not approval — it records the debt. A fixture added or
   regenerated from now on must carry the block; a name leaves the list only by gaining one. The
   test also fails if the list goes stale.

**Status:** items 1 and 6 are implemented (the block's shape is defined and enforced for new
files). Items 2–5 are **proposals** and are not implemented — they change evaluator behaviour and
need your approval first.

## Phase 6 — resource and lifecycle audit

### 6.1 `-W error::ResourceWarning` does not work here

The brief suggests running the suite with `python3 -W error::ResourceWarning`. It does not fail
these warnings, and relying on it would give false confidence: a `ResourceWarning` for an
unclosed sqlite connection or file is emitted from the object's finaliser during garbage
collection, where Python swallows exceptions. The suite still reports `OK` with the flag set.

Allocation sites were found instead with `python3 -X tracemalloc=15 -W always::ResourceWarning`,
which prints the traceback of the *allocation* rather than the collection.

### 6.2 All 14 warnings are allocated in test code

| test site | kind | what it opens |
|---|---|---|
| `tests/test_leadlag.py` 378, 404, 433, 587 | sqlite | `Store(":memory:")` |
| `tests/test_leadlag.py:671` | sqlite | `LagPaperBook(store=Store(db), …)` |
| `tests/test_store.py` 49, 50, 61, 68 | sqlite | `Store(...)` |
| `tests/test_store.py:63` | sqlite | `sqlite3.connect(self.path)` |
| `tests/test_weekscan.py:177` | sqlite | `Store(":memory:")` |
| `tests/test_arbbutton.py` 150, 207 | file | `open(path)` inside a comprehension |
| `tests/test_order_ledger.py:424` | file | `open(f, "rb")` inside a join |

Every one passes through `arb_engine/store.py:171` (`sqlite3.connect`) or a bare `open()` in the
test itself. **No production code path leaks.** These are test helpers that build a `Store` and
never close it; the fix is `addCleanup(st.close)` (or a `with` block for the file reads).

### 6.3 Production lifecycle is sound, with three exceptions

Verified by reading the ownership of each resource:

* **Thread pools** — `fastlane.py:191` and `:268` both use `with ThreadPoolExecutor(...)`, so
  workers are shut down on exit, including on an exception.
* **The background trade-print thread** — `fastlane.py:303` starts a `daemon=True` thread. It is
  not orphaned: `poll_trades` refuses to start a second one while the first is alive
  (`_trade_lock`, `:301`), and `wait_for_trade_polls()` (`:308`) joins it with a bound before the
  `Store` may be closed. That method **is** called in production, at `live.py:509`, with a
  timeout of `max(5.0, fast * 3 + 5)`. The design intent — a slow trade request must not delay L1
  recording, but must not be killed mid-write either — is implemented.
* **Preflight threads** — `preflight.py:410` starts daemon threads and joins each with a deadline
  at `:418`.
* **HTTP** — `venues/http.py:189` uses `with urllib.request.urlopen(...)`. There is no persistent
  session or opener to leak.
* **No `Store` is constructed inside a loop** anywhere in `arb_engine/` or `scripts/` (checked by
  walking the AST of every function), so there is no unbounded growth.

The three constructions with no matching `close()`:

| site | command | assessment |
|---|---|---|
| `arb_engine/cli.py:312` | `cmd_inplay` | long-running; the OS reclaims at exit, but the WAL is not checkpointed cleanly |
| `arb_engine/cli.py:403` | `cmd_live` | same |
| `arb_engine/cli_plugins/weekscan_flags.py:31` | week scanner `run` | same |

With a ~10 GB `history.db` in WAL mode this is not corruption — sqlite recovers the WAL on the
next open — but a clean close on shutdown is cheap and makes the next start faster.
`arb_engine/cli.py` is off-limits for feature work under AGENTS rule 8, so the two `cli.py` sites
are **reported, not changed**; a fix belongs with the loaders' owner.

**Implemented:** nothing changed in this phase yet.
**Tested:** nothing yet — the test-helper closures are applied after the subsystem branches merge,
to avoid editing the same test files two ways.
**Empirical:** none; this phase reads code and allocation traces only.
**Assumptions:** that daemon-thread termination at interpreter exit cannot corrupt sqlite. That
holds for sqlite's transactional writes — an interrupted write rolls back — but an interrupted
trade-print batch is **silently lost**, and the recorder keeps no record that it was dropped.
That gap belongs to the recorder audit, not here.

### 2.1 The single most serious finding: the production clocks were pinned

`LiveSlate.run()` called `tick(t0)` and `_fast_loop` called `fast_step(s0)`. Every timing branch
in those methods is guarded by `pinned is None`, and **the tests call `tick()` with no argument**.
So five behaviours were exercised by the suite and dead in production:

* the polling-gap record (`live.py:255`),
* the request/response boundary on each adapter fetch (`live.py:192`, `:195`) — with the clock
  pinned, `req_ts == obs_ts == t0` on every full-tick row while `approx_time=0` claimed it exact,
* the carried-quote guard (`live.py:197`) — **a silent regression of commit `91ac811`**, which was
  written to stop cached Robinhood prices being stamped freshly observed. Up to 30-minute-old
  catalogue prices were recorded `refreshed=1, approx_time=0`,
* the post-fetch clock refresh (`live.py:283`),
* the per-game decision time (`live.py:300`).

In the fast lane `obs_ts` was the *step's start* although the response arrived later, so an
observation was stamped **before its own response** — a look-ahead in the recorded dataset, not a
rounding error.

**Consequence that cannot be repaired.** Every fast-lane row written before this fix carries
`obs_ts` = step start with `approx_time=0`. The true receipt times were never stored. Any research
result that relied on `obs_ts <= decision_ts` over those rows should be re-run after re-recording,
and rows already in `history.db` should be treated as approximate. This audit did not read the
deployed database, so the size of the contamination is unmeasured.

### 2.2 Silent data loss in the print poller

`trades.extend(page.get("trades") or [])` read a page with no `trades` key as an empty page. The
cursor was then `None`, so the walk was declared **complete** and the watermark advanced to the
newest buffered print. Kalshi pages newest-first, so every older print behind the unreached cursor
was skipped **permanently** — a hole nothing would refill. `KalshiClient.paged` already had the
opposite rule in the same class: a page without its list is a failed read, not an empty one.

A repeating cursor was worse than a loop: each poll re-buffered `max_pages` of prints, recorded
nothing, reported nothing, and the ticker stayed backlogged for the life of the process with
unbounded memory growth. Measured: 20 HTTP pages over 4 polls, buffer 5 → 20, **0 rows recorded,
0 errors raised**.

Also fixed there: a NaN exchange timestamp violated `ts REAL NOT NULL`, so `INSERT OR IGNORE`
dropped the print with no row, no error and no count — unreadable looked exactly like absent; and
one `inf` timestamp broke `latest_trade_ts` for that ticker **permanently**, so every later poll
of it raised before recording anything.

### 2.3 Ledger: the eight known defects, and one new one

All eight reproduced at `6b81375` and are fixed. The two that could cost real money silently:

* **H6** — reconcile listed orders with `min_ts = local created_ts − 60`, and Kalshi filters on
  *its* clock. With the local clock ahead, the accepted order was filtered out of a "complete"
  listing and released as never accepted, while the exchange showed it `executed`. A filtered
  listing can no longer prove absence: an unfiltered listing of the ticker is read first.
* **H10** — `KalshiBroker.poll` read a missing fill count as 0 and stopped tracking on a terminal
  status, so a resting maker order that had filled reported **no fills** to the runner and no
  hedge was ever raised. A naked maker fill.

**H16** deserves a note because its effect is the opposite of what it looks like: fills were keyed
by `fill_id` before `trade_id`, so one trade listed under two fill ids counted twice, which
produced a *false contradiction* — and a contradicted intent can never be hedged. A real position
became permanently unhedgeable.

**s17** gained a precision the earlier audit did not have: another entry's hedge counts as this
entry's exit **only when the lock is on the entry ticker's other side**. A lock on the sibling
market ticker was never counted, so the defect was intermittent by market shape.

New: `reserve(count=inf)` raised `OverflowError` out of a method documented to answer with a
`Reservation`. `lagexec._send` and `broker.place` catch only `LedgerError`, so it killed the loop.

### 2.4 Trade cache: round 4

Three rounds had already hardened this. Round 4 found what they missed:

* a complete tape stamped in the **reader's future** was served — the closed-window rule was
  measured from `pass_started_at`, a number the *writer* recorded, never compared with the
  reader's clock. A writer 2000 s fast cached a short tape as complete and a correct reader was
  served it, losing a late print for good. Schema 3 → **4**, so every existing file is discarded
  once and refetched. Both clones currently hold no trade cache, so this is a no-op in practice;
* a cache file did not say whether it was **fetched or asserted**. `store_complete` wrote a file
  indistinguishable from a paginated fetch. Files now carry `source`, and reading an asserted tape
  logs a warning;
* without `fcntl`, a late writer threw finished tapes away — 6 of 6 runs left an incomplete file
  where a complete one had been written; 0 of 6 after an `O_EXCL` fallback lock.

Fuzz: 4,000 seeds, 89,712 client calls, 22,216 kills mid-fetch and mid-write, **0 invariant
violations**. Concurrency: 3 × 72 worker runs, 0 wrong tapes, 0 downgrades.

The phase reported an honest negative result worth keeping: an earlier fuzz produced violations,
and tracing showed the cause was the *fake venue*, not the client — the model re-issued a cursor
that jumped pagination forward. An opaque-cursor client cannot detect a forward skip; there is no
in-band evidence of a gap. That is a real, unfixable-in-principle assumption, kept visible behind
a `--lying-venue` flag.

### 2.8 Separation of evidence

**Implemented** — everything in 2.1–2.5 is in the code and exercised by the suite.

**Tested** — 154 new tests across four modules, every one offline: fake HTTP clients, injected
clocks, temp-dir stores, synthetic fixtures. 67 of them were verified to fail on `6b81375`, and
phase 2's 14 fix hunks were each reverted individually and caught.

**Empirical** — offline measurements only: the fuzz and concurrency counts in 2.4; a fast-lane
step against a 1.5 s venue going 1.51 s → 0.20 s under a 0.2 s budget; the repeating-cursor
measurements in 2.2; `Store._lock` held 0.7 ms per 100 prints and 34.7 ms per 5,000, three orders
of magnitude under the 1 s lane. **No venue was contacted, no recorded database was read, no
replay was run, and no fold was opened.**

**Assumptions that remain** — Kalshi's cursors are consistent (a forward skip is undetectable);
`min_ts` is inclusive (taken from a code comment, unverifiable offline); venue publication lag
plus local clock skew stays under the 15-minute settle margin; one Kalshi trade produces one fill
per order (so a repeated `trade_id` is a duplicate); what `taker_fill_cost_dollars` means for a
*sell* is unestablished, so the cost bound is applied to buys only. `MAX_CONTRACTS` and the
50,000-print backlog cap are judgement calls, not venue facts.

**A passing suite is not evidence of profitability or of live safety.** It says these specific
properties hold on these specific offline fixtures. By this audit's own finding, the recorded
fast-lane data is *not* causally clean, and nothing here has run against a live venue.
